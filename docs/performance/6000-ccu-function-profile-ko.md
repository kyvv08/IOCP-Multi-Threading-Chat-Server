# 6,000 CCU 함수별 표본 타이밍 보고서

## 시험 조건

| 항목 | 값 |
|---|---:|
| 서버 | ChatServer Release x64, 1개, 포트 17777 |
| 부하 생성기 | DummyClient 2개 프로세스 |

| 서버 최대 접속 | 6,000 CCU, 누적 수락 6,000 |

서버를 새로 시작한 직후 클라이언트 두 개를 실행해 유휴 서버 시간이 함수 표본에 섞이지 않도록 했습니다. 함수 계측은 `ChatServer.exe 17777 --profile`로 명시적으로 활성화하며, 일반 Release 실행에는 계측을 사용하지 않습니다. 테스트 동안 연결 해제는 양쪽 모두 0건이었습니다. 전체 측정 실행은 클라이언트 시작·종료 과정을 포함해 325.9초였습니다.

## 수집 방법과 해석 범위

WPR CPU와 CPU.light 방식은 각각 약 92.9GB, 59.1GB의 ETL을 만들었고 이벤트 손실 59,467,862개, 137,978,475개를 보고했습니다. Xperf도 디스크 대역폭 부족으로 데이터가 신뢰하기 어렵다고 판정했습니다. 사용자의 요청에 따라 두 ETL을 삭제하고, ETW를 사용하지 않는 서버 내부 표본 계측으로 전환했습니다.

다음 7개 함수에서 각 스레드별 호출 64회마다 한 번씩 함수 진입과 반환 시각을 기록했습니다. `steady_clock`으로 벽시계 경과시간을 재고, `QueryThreadCycleTime`으로 해당 스레드에 누적된 CPU 사이클 차이를 읽었습니다. 평균 호출 수와 누적값은 표본값에 64를 곱한 추정치입니다.

벽시계 시간은 락 대기와 스레드 선점 시간을 포함합니다. 스레드 CPU 사이클은 대기 구간을 제외하지만, 바깥 함수 안에서 실행된 하위 함수의 사이클도 포함합니다. 함수 측정이 중첩되므로 누적값끼리 더할 수 없고 CPU 사이클을 시간 단위로 환산하지 않았습니다. Windows 문서도 `QueryThreadCycleTime` 값을 경과시간으로 변환하지 말라고 안내합니다.

## 병목 판단

### 채팅 브로드캐스트의 수신자별 송신 경로가 우선 후보

`Session::Send`는 약 **1억 3,718만 회**로 추정됩니다. 평균 스레드 CPU 사이클은 호출당 약 6,529이며, 수신자별 송신량이 팬아웃 비용을 좌우합니다. [`Room::Broadcast`](../../Source/ChatServer/Room/Room.cpp)는 평균 약 329,352 사이클, [`Room::HandleChat`](../../Source/ChatServer/Room/Room.cpp)은 약 392,303 사이클입니다. 이 값은 하위 호출 비용을 포함하므로 직접 합산하면 안 됩니다.

`JobQueue::Execute`는 평균 약 234,800 사이클이며 내부에서 채팅 작업을 실행합니다. 따라서 하위 함수의 사이클이 함께 포함됩니다. 이 값은 JobQueue 자체의 독점 비용이 아니라 작업 전체의 포괄 비용입니다.

`GlobalQueue::Pop`은 약 3,698만 회, 평균 약 1,617 사이클입니다. `JobQueue::Push`와 `GlobalQueue::Push`는 각각 약 2,071, 1,487 사이클로 관측됐습니다. 큐 경합 여부는 이 계측만으로 확정할 수 없으므로 RTT와 후속 변경 비교를 병행해야 합니다.

### 메모리보다 CPU 처리량과 꼬리 지연시간이 먼저 부담

6,000 CCU에서 RTT p95는 약 23ms, p99는 약 31ms였습니다. 서버 CPU 평균은 1.67코어, 작업 집합은 약 88MB였습니다. 이 실행에서는 메모리 압박이 관찰되지 않았습니다. 함수 사이클 표본은 송신 팬아웃과 룸 처리 경로에 비용이 모이는 것을 보여주지만, 포괄 시간이라 독점 CPU 점유율로 해석하지 않습니다.
